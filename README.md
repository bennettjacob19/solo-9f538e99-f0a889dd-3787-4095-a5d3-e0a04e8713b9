# 磁带灾备恢复演练（Flask）

灾备值班员只有一台带机、两盘磁带，需要从带卷还原虚拟机镜像。本项目用本地文件
模拟磁带卷，提供一个 Flask 网页来选择带卷、填写**读带块数上限**与**暂存块数
上限**，并在额度内完成恢复演练；遇坏块或额度不足时报错，且保留上一次成品。

成品盘快满时，还可在网页选择**两份尚未整理的等长成品镜像**、填写整理期间允许
**多占的 4 KiB 块数**做块级整理（去重）：同一块号上内容相同的块只留一份；
余量刚够写一份镜像的差异块时也能完成；整理期间、失败后与成功后，两份成品都能
从原链接完整下载且字节不变（重启后也一样）。

## 磁带与恢复语义（按演练规则实现）

- 每套带卷最多两盘磁带、合计最多 12 个 **4 KiB** 镜像块；`manifest.json`
  记录每块的镜像块号、所在磁带、带上帧位置与 SHA-256，每块只出现一次。
- 磁带只能**从头顺读**。换带或回卷后，磁头回到第 0 帧；同一盘带在一次顺读
  会话内磁头自然前移，目标帧落后于磁头时才回卷。
- 顺读路径上**跳过的帧也算读带量**，回卷/换带后**重读的帧重复计数**。
- 提前读到、暂时不能按块号写出的块进入**暂存区**（内存/磁盘等价，本实现用
  内存承载，落盘镜像走临时文件），暂存块数峰值受暂存额度约束。
- 镜像只允许按块号 0、1、2…… **顺序追加**，不能回读、不能改已写块。
- 每个块在**入暂存前**与**写出前**都核对 SHA-256；坏块立即失败。
- 任一额度不足或遇到坏块立即中止，删除半成品 `image.bin.part`，**上一次
  成品 `image.bin` 原样保留**；恢复期间仍可下载上次成品（原子发布）。

## 目录结构

```
app/
  storage.py      带卷发现、manifest 校验、定长帧顺读
  engine.py       恢复引擎：磁头/换带/回卷、读带与暂存额度、摘要核对、只追加写
  store.py        成品块仓库：段文件 + 块清单(image.json) + 引用计数、启动恢复
  consolidate.py  成品整理（块级去重）：逐块只读比对、差异块临时段、原子提交
  web.py          Flask 应用、后台任务、任务状态、成品下载（整镜像/清单拼流）
  templates/      单页界面（选带卷、填额度、选两份成品做整理、状态与下载）
scripts/
  make_samples.py  生成五套样例带卷
tests/            引擎与 Web 自测（37 个用例）
run.py            本地开发入口
Dockerfile, docker-compose.yml
```

## 成品整理（块级去重）语义

- 整理**只读成品**（`image.bin`），不碰带卷；只接受两份**尚未整理**的
  **等长**镜像（4 KiB 的整数倍）。
- 逐块（4 KiB）计算 SHA-256 并按块号比对：同号同内容块只留一份。
- 第一份成品整体**硬链**为共享段（零拷贝、零额外镜像数据占用）；第二份的
  **差异块 D 个**写入新段的临时文件（这部分数据同样计入额度），因此整理期间
  镜像数据的额外占用峰值**恰好为 D 块**，额度等于差异块数时即可完成。
- 提交顺序（先落差异段 → 硬链共享段 → 写两份块清单 → 删整镜像）配合
  启动时 `BlockStore.recover()` 对账，崩溃后无需日志即可收敛：孤儿段与
  临时文件被清理、残留整镜像补删、有效清单继续可用。
- 整理期间与失败后两份成品都可从原链接完整下载；成功后原链接仍返回**相同
  字节**，重启后也一样（清单落盘，引用关系启动重建）。
- 页面显示**实际省下的镜像数据块数**（即同号同内容块数 S；稳态镜像数据
  从 2N 块降到 N+D 块）。
- 日后重新恢复其中一套带卷：新整镜像原子发布后，从原链接发起的**新下载
  拿到新成品**，另一份仍返回原字节；引用归零的旧块立即释放文件名，在途
  下载持有的 fd 钉住 inode，空间随最后一个 fd 关闭释放——**已开始的下载
  读完当时的成品**。
- 已整理成品下载时按清单从段文件拼流，并**逐块核对 SHA-256**。

## 五套样例带卷（`scripts/make_samples.py` 生成）

| 带卷 | 布局 | 读带量 | 暂存峰值 | 换带 | 回卷 |
|---|---|---|---|---|---|
| `sample-ordered` | 块号沿顺读方向递增，块 0 在带头 | 12 | 0 | 1 | 0 |
| `sample-scrambled` | 每盘带块号沿顺读方向递减，未来块必须暂存 | 12 | 10 | 1 | 0 |
| `sample-bad` | 同乱序布局，块 11 带数据被故意损坏 | 失败 | — | — | — |
| `sample-pair-a` | 整理演练对（顺序布局，12 块），与 b 的**前 8 个同号块内容相同** | 12 | 0 | 1 | 0 |
| `sample-pair-b` | 与 a 等长；前 8 块相同、**后 4 块各自不同**（差异块） | 12 | 0 | 1 | 0 |

> 页面上每套带卷会显示“预估读带/暂存”，即贪心策略（提前读到的块全部暂存）
> 下的额度下限，与真实模拟同源计算。
> 先恢复 `sample-pair-a`、`sample-pair-b` 得到两份成品，即可在“成品整理”
> 卡片选这两份、额度填 4（= 差异块数）完成整理，页面显示省下 8 个镜像数据块。

## 本地运行

```bash
# 1) 安装依赖（无 pip/venv 的隔离环境可装到独立目录并用 PYTHONPATH 引用）
pip install -r requirements.txt

# 2) 生成样例带卷
python -I scripts/make_samples.py --root data/tapes

# 3) 启动（默认 0.0.0.0:8000）
python -I run.py
# 或 gunicorn（与容器一致，单 worker 多线程以保证任务状态语义）
python -m gunicorn --bind 0.0.0.0:8000 --workers 1 --threads 4 run:app
```

环境变量：`TAPE_ROOT`（带卷根目录，默认 `data/tapes`）、
`OUTPUT_ROOT`（成品目录，默认 `data/output`）、
`READ_DELAY`（每读一块的模拟延迟秒数，默认 `0.05`，设 0 最快）、
`CONSOLIDATE_DELAY`（整理时每写一个差异块的模拟延迟秒数，默认 `0.05`）。

## Docker Compose

```bash
docker compose up --build
# 打开 http://localhost:8000
```

镜像内置五套样例带卷；带卷与成品分别挂载在命名卷 `tape-data`、`output-data`
（`/data/tapes`、`/data/output`）。块仓库位于成品卷内的 `_store/` 目录，
容器重启后从磁盘清单自动恢复引用关系并收敛中断的整理提交。

## 实现、验证与未完成项

### 已实现
- 带卷清单严格校验：块号连续、每块唯一、帧位置连续、带文件大小精确匹配、
  最多 12 块/两盘带、目录名防穿越。
- 完整磁带机械语义：挂带、换带、磁头前移、回卷，跳过与重读均计读带量。
- 双额度约束与贪心暂存策略；页面给出每带卷的额度下限预估。
- 只追加镜像输出（内存 sink 供测试，文件 sink 经 `.part` + `os.replace`
  原子发布），入暂存与写出两次摘要核对。
- 坏块/额度不足失败即停、保留上次成品；恢复中可下载；任务状态与实际
  读带块数、暂存峰值、换带/回卷次数、事件流页面轮询展示。
- 成品块仓库（`app/store.py`）：段文件 + `image.json` 清单 + 引用计数；
  整镜像硬链为共享段零拷贝，差异块写临时段；提交顺序 + 启动 `recover()`
  保证崩溃收敛；下载在锁内预开 fd 钉住快照，按清单拼流并逐块核 SHA-256。
- 整理算法（`app/consolidate.py`）：只读比对、额度即差异块数、失败零残留、
  页面展示实际省下的镜像数据块数；重新恢复自动释放旧块、链接语义不变。
- 新增 `sample-pair-a` / `sample-pair-b` 成对样例（有相同块也有差异块）。
- Dockerfile + docker-compose，镜像内置样例。

### 已验证
- 37 个单元/集成测试全部通过（`python -I -m unittest`）。
- 端到端磁盘占用脚本验证：镜像数据峰值多占恰为差异块 4 块（临时段计入，
  清单等元数据不计入镜像数据）；稳态从 24 块降到 16 块、省下 8 块；
  额度 3 失败且零残留；完全相同成品额度 0 可整理；重启与重新恢复语义正确；
  在途下载快照不受替换/释放影响；旧块随引用归零（含 fd 关闭）释放。
- 端到端脚本验证：成功交付 49152 字节镜像并逐块核对 12 个 SHA-256；
  读带/暂存额度不足与坏块均正确报错且成品保留；恢复中下载与并发拒绝生效。
- gunicorn 单 worker 多线程实际启动，`/`、`/status`、`/download`、
  `/consolidate` 均工作正常。

### 未完成 / 限制
- 本环境无 docker 二进制，compose 配置仅做静态校验，未实际 `docker build`
  （Dockerfile/compose 与原结构保持兼容，仅新增样例与环境变量）。
- 任务状态保存在单进程内存中（因此 gunicorn 固定单 worker）；多副本
  部署或进程重启后任务历史不保留（成品文件与块仓库清单仍在，重启自动恢复）。
- 暂存实现为内存承载，未单独模拟“暂存写磁盘”的独立 IO 额度；按题意内存与
  磁盘暂存等价，统一计入暂存块数额度。
- 块仓库假设成品卷支持硬链（本地卷/常规容器卷均支持）；不支持时自动退化为
  改名，提交窗口内第一份成品短暂无文件名（清单原子发布后即恢复可下载）。
